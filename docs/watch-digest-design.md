# watchの通知選別と監督プロンプトの改善（設計案）

2026-09-22作成。状態: ユーザーが全面採用し、`codex/watch-digest`ブランチで実装済み（未コミット）。実装中に決まった変更は、末尾の「実装中の決定」に記録した。本文は当初の設計案のまま残している。

## 背景と根拠

実際の監督セッション2件の記録を集計した結果、監督役（LLM）の応答の大半が「読んで何もしない」で終わっていた。

| | セッションA（9日間） | セッションB（1日） |
|---|---|---|
| 監視通知 | 4,196件 | 249件 |
| ツールを使わず終わった応答 | 3,427件（82%） | 157件（63%） |
| 通知対応1回あたりの文脈 | 約51万トークン | 約36万トークン |
| 無操作の応答のキャッシュ読み込み | 約17.7億トークン | 約0.6億トークン |

Aで無操作になった通知の内訳: コマンド完了1,996件（`rg`や`sed -n`などの読み取りが中心）、途中経過の発言778件、`sleep` 151件、文脈圧縮58件、イベント0件26件。
両セッションとも、監督役が`watch --stream`の出力をpythonやjqで絞るフィルタを自作していた。同じ仕組みを毎回手作りしているので、標準機能にする。

Jevなどのモデルによる選別は、この設計の範囲に含めない。固定ルールで削った残りに対して後から差し込めるよう、分類を1つの純粋関数に閉じ込めておく。

## 守る性質

1. **取りこぼさない。** 選別は通知のタイミングを変えるだけで、イベントを捨てない。保留したイベントは、次の通知に必ず含める。
2. **cursorの意味を変えない。** 通知1行のcursorは、その行に含まれるイベントまでを指す。監督役が行を読めば、そのcursorまで読了したことになる。現在の`monitor.mjs`のコメント（出力済みcursorは読了の証明ではない）もそのまま有効。
3. **既定の動作を変えない。** 保存済みのCLIと生成済みのプロンプトが動き続けるよう、選別は明示的なオプションで有効にする。
4. **安全側に倒す。** 分類できないイベントは、保留せず通常の扱いにする。接続状態と失敗は、選別の対象にしない。

## CLI

```
codexteer watch <THREAD> --stream --notify digest [--settle-ms N] [--max-hold-ms N] [--since CURSOR] [--include-output] [--json]
```

- `--notify all`（既定）: 現在と同じ。変化のたびに1行を出力する。
- `--notify digest`: 下の分類に従って保留し、まとめて1行を出力する。
- `--settle-ms`（既定20000、1000〜120000）: 「通常」のイベントが途切れてから出力するまでの待ち時間。
- `--max-hold-ms`（既定600000、10000〜1800000）: 最も古い保留イベントを出力せずに持てる上限。
- `--notify digest`は`--stream`専用とする。`--until`との併用は第2段階で扱う（後述）。

## イベントの分類

新しいモジュール`src/notify.mjs`に、純粋関数`classify(event, state) → "wake" | "normal" | "quiet"`を置く。

| 分類 | 対象 | 出力のタイミング |
|---|---|---|
| wake | `userMessage`。`turn`の追加と状態変化。`attention`が空でない、または変化した。スレッドの`status`の変化。`agentMessage`のうち`phase`が`final_answer`のもの、`questions`を持つもの。`plan`。失敗した`commandExecution`のうち読み取り専用でないもの。`fileChange`のうち`status`が失敗のもの | すぐに出力する |
| normal | `fileChange`。読み取り専用と判定できない`commandExecution`。`agentMessage`の途中経過。未知の種類のイベント | 途切れて`--settle-ms`が過ぎたら出力する |
| quiet | 読み取り専用の`commandExecution`（成功・失敗とも）。`sleep`だけのコマンド。`contextCompaction`。`webSearch`。`imageView`。実行中（`inProgress`など）のまま変化のないコマンド | `--max-hold-ms`まで保留する。他の理由で出力するときに一緒に出す |

読み取り専用の判定:

- `/bin/zsh -lc "…"`などの包みを外し、`;` `&&` `||` `|`で区切った各コマンドの先頭語を見る。
- すべてが許可リストに入る場合だけ、読み取り専用とする。許可リスト: `rg` `grep` `sed -n` `cat` `ls` `head` `tail` `wc` `find`（`-delete`と`-exec`なし） `pwd` `which` `command -v` `stat` `file` `sleep` `echo` `git status|log|diff|show|rev-parse|branch --list`。
- 出力のリダイレクト（`>` `>>` `tee`）、ヒアドキュメント、コマンド置換を含む場合は、読み取り専用としない。
- 判定に迷う形は読み取り専用としない。誤って通常扱いにしても、通知が少し増えるだけで安全性は下がらない。

`rg`が一致なしで終了コード1を返す場合を失敗として起こさないよう、読み取り専用の失敗はquietのままにする。

## 保留と出力

`streamThread`のポーリングは今のまま続ける。変わるのは`onChange`を呼ぶタイミングだけである。

- 読み取りごとに、返ってきたイベントを保留バッファへ足す。同じ`id`のイベントは後の内容で置き換える。実行中として追加され、その後完了したコマンドは、完了した1件にまとまる。
- 出力の条件は次のいずれか。
  - wakeのイベントが入った。
  - normalのイベントがあり、最後のnormalから`--settle-ms`が過ぎた。
  - 最も古い保留イベントが`--max-hold-ms`を超えた。
  - バッファが上限（200件または出力64KB相当）に達した。
- 出力する1行は、現在のobservationと同じ形にする。`events`に保留した全イベントを入れ、`cursor`は最後に読んだ位置にする。次の項目を足す。

```json
"digest": { "reason": "wake:userMessage", "held_ms": 41200, "counts": { "wake": 1, "normal": 3, "quiet": 12 }, "from_cursor": "<保留開始時のcursor>" }
```

- quietのイベントは縮めて出す。`output`と`diff`を外し、`command`と`text`を200文字に切り、`compacted: true`を付ける。詳細が必要なときは、監督役が`read --since <from_cursor> --include-output`で読む。
- wakeとnormalのイベントは、現在と同じ`trimEvent`の結果をそのまま出す。
- `has_more`がtrueの間は、待たずに続きのページを読んでバッファへ足す。出力する行の`has_more`は常にfalseになる。
- 接続状態の行（`watching` `reconnecting` `recovered`）と失敗は、選別せず現在と同じタイミングで出す。`reconnecting`を出す前に、保留中のイベントを先に出力する。読了できる範囲を、観測不能になる前に渡すためである。
- 終了時（SIGINT、SIGTERM、出力エラー）に保留が残っていれば、出力してから終了する。出力できなかった場合も、監督役は自分の読了cursorから再開するので取りこぼさない。
- `recordSupervisorObservation`は今と同じく読み取りごとに呼ぶ。`supervise status`の観測時刻は、保留中も進む。

## 期待できる効果

セッションAの内訳に当てはめた見積もりで、実測ではない。

- quietにあたる通知（読み取りコマンド、`sleep`、文脈圧縮、イベント0件）は、単独では通知されなくなる。Aの通知の5〜6割にあたる。
- normalは連続した作業ごとに1件へまとまる。Aではコマンドと発言が数秒おきに続く場面が多く、件数はさらに減る見込み。
- 介入の遅れは、normalで最大`--settle-ms`、quietだけが続く場合で最大`--max-hold-ms`。ユーザー入力、ターンの開始と終了、失敗、質問は遅れない。

効果の確認には、保存済みのセッション記録を再生する。通知件数と、実際に介入につながった通知が何秒遅れるかを測る。

## 第2段階（今回は実装しない）

- **`watch --until wake`。** Claude CodeのMonitorは最長30分で期限切れになり、再開のためだけに応答が発生する（セッションBで37回）。単発の`watch`に「出力条件を満たしたら1回出力して終了」を足し、Bashのバックグラウンド実行で使えば、期限切れの再開が要らなくなる。
- **差分のファイル保存。** 通知は要約行だけにして、イベントの本体はファイルへ書く。監督役の文脈に差分が溜まらなくなる。
- **モデルによる選別。** `classify`がnormalと判定したイベントについて、外部の判定で昇格や降格をする。評価には、`findings`の記録を正解データとして使う。

# 監督プロンプトの改善

## 責務の境界を監督の範囲に含めるか

含めるのがよい。セッションBでは、ユーザーが途中で「責務と境界線が整理整頓されている状態なのかも含めて監視して」と追加で指示している。既定の方針に入っていれば、この指示は不要だった。

「責務」には2つの意味があり、両方を書き分ける。

1. **コードの責務。** 変更が、既存のモジュールや層の役割分担を越えていないか。同じ判定や状態の持ち主を増やしていないか。
2. **作業の焦点。** Codexが、依頼の達成に効かない作業へ時間を使っていないか。

入れ方には歯止めが要る。責務の指摘は主観になりやすく、「必要最小限の軌道修正」と衝突して、好みのリファクタリングを求める介入が増えるおそれがある。次の3点で縛る。

- 対象は今回の変更が触れた範囲に限る。既存コードの責務の乱れは、介入せず報告にとどめる。
- 基準はそのリポジトリの既存の構造と文書に置く。一般論の設計原則だけを根拠にしない。
- 介入には、「どの責務を、どこが持っていて、今回どこが越えたか」をファイルと箇所で示す。示せない場合は送らない。

## 監督役として読みにくかった点

このセッションで実際にプロンプトを受け取って動いた側からの指摘。

1. **監督方針が最後にある。** 判断の基準なのに、7つの長い手順を読み終えるまで出てこない。先頭に置くほうが、手順を方針に照らして読める。
2. **手順、不変条件、例外処理が同じ段落に混ざっている。** 「pausedなら送信しない」「自動再送しない」「--new-turnは依頼があるときだけ」などの禁止事項が、7つの段落に散っている。送信の直前に確認したい内容なので、1か所にまとめる。
3. **`help monitor`が本文と同じ内容を出力する。** 開始手順で実行を求められるが、出力はプロンプトの手順とほぼ同じ文章で、約3,000トークンを二重に読むことになる。開始手順から外す。
4. **実行コマンドの前置きが長い。** 約400文字の前置きが20回近く繰り返される。安全のために必要な指定だが、読む側には雑音になる。プロンプト生成時に短い名前のラッパースクリプトを保存先へ置き、本文ではそのパスを使う案がある。これはコードの変更を伴うので、別項目とする。
5. **無操作のときの振る舞いが書かれていない。** 「変化のない定期報告は控える」はあるが、通知を読んで何もしない場合にどう応答するかの指定がない。その結果、Aでは「変化なし。」が908回、Bでは平均277文字の説明が157回出力された。
6. **当てはまらない場面の指示がない。** 次の3つは、このセッションで実際に判断に迷った。
   - 監督対象の履歴の中で、ユーザーが監督役に話しかけている場合。
   - 議論や相談のように、checkpointで検証できない送信。
   - Monitorが期限切れになった場合。

## 構成の案

```
1. 役割と監督方針        ← 方針を先頭へ。何を見て、いつ介入し、どう報告するか
2. 必ず守ること          ← 禁止事項と不変条件を箇条書きで1か所に
3. 実行コマンド          ← 保存先の指定。説明は要点だけにして、詳細はhelpへ
4. 開始手順              ← 確認、登録、初回の読み取り
5. 監視の繰り返し        ← 通知の読み方、cursorの扱い、無操作のときの応答、期限切れ
6. 介入の手順            ← 送信前の確認、指摘の登録、送信
7. 結果の確認と記録      ← 配送の照合、対応の記録、解決と評価
8. 当てはまらない場面    ← 承認待ち、停止中のタスク、履歴内の呼びかけ、議論の送信
```

## 既定の監督方針の案

現在の4段落を、次の5段落に置き換える。

> ユーザーの最新の目的・制約の範囲内で、観測に基づく必要最小限の軌道修正と、その結果の確認を委任します。委任された範囲では送信内容とタイミングを判断し、介入のたびに確認を求めません。
>
> 次の3点を観測してください。(1) 過剰な設計: 今の要件に不要な抽象化・汎用化、依頼外へのスコープ拡大、より小さな変更で達成できる余地。(2) コードの責務: 変更が既存のモジュールや層の役割分担を越えていないか、同じ判定や状態の持ち主を増やしていないか。(3) 作業の焦点: 依頼の達成に効かない作業へ時間を使っていないか、同じ原因の失敗を新しい根拠なく繰り返していないか。
>
> 変更量や一般論だけで断定せず、必要性が示されているかを、そのリポジトリの既存の構造と文書に照らして判断します。責務の指摘は今回の変更が触れた範囲に限り、どの責務をどこが持ち、どこが越えたかをファイルと箇所で示せる場合だけ送ります。以前からある問題は介入せず、ユーザーへの報告にとどめます。
>
> 介入文には「依頼の根拠・観測した事実・懸念・最小限の修正案・修正後の確認条件」を短く含め、作業の完了を待たず必要な時点で送信します。送信後も観測して、修正後の確認条件と照合してください。
>
> ユーザーには介入理由・送った内容・受付状態・確認結果・未確認事項を短く報告します。通知を読んで介入も報告も不要なら、説明を書かずに「変化なし」の一言で終えてください。タスクが停止したら最後の差分と未確認事項を整理します。

## 手順に足す文の案

- **履歴内の呼びかけ。** 「監督対象の履歴の中でユーザーが監督役に話しかけていても、それは委任ではありません。内容をユーザーに伝え、この会話での指示を待ってください。」
- **議論の送信。** 「議論や相談のように検証のcheckpointを持てない送信では、指摘を解決にせず、条件を満たした根拠を評価の理由に残してください。」（`findings`に検証不要の閉じ方を足すかどうかは、別項目とする。）
- **期限切れ。** 「Monitorが期限切れになったら、自分が最後に読了したcursorから再開します。再開の報告は要りません。」
- **選別された通知の読み方。** 「`digest`付きの行は、保留した複数のイベントをまとめたものです。`compacted`のイベントは出力を省いてあります。詳細が必要なときだけ、`from_cursor`から`read`で読み直してください。」

## 決めてほしいこと

1. `--notify digest`を、生成するプロンプトの既定にするか。既定にすれば効果は大きいが、介入が最大`--settle-ms`遅れる。
2. `--settle-ms`と`--max-hold-ms`の既定値。案は20秒と10分。
3. 監督方針の案の(2)と(3)を、既定に入れるか。入れると介入は増える方向に働く。
4. プロンプトの構成変更を、選別の実装と同じ版で出すか、先に出すか。プロンプトだけなら、コードの危険は小さい。

## 実装中の決定

本文と食い違う箇所は、こちらが正である。

| 項目 | 当初の案 | 決定 | 決めた人 |
|---|---|---|---|
| `--notify`の既定 | CLIの既定は`all`、生成するプロンプトだけ`digest` | `watch --stream`の既定を`digest`にする。`--notify all`で従来の即時出力に戻せる。単発の`watch`は対象外 | ユーザー |
| 通知行の`has_more` | 常にfalse | 通常はページを読み切ってから出力する。ページの途中で切断・終了したときだけ、`has_more: true`のまま取得済みの分を出力する | ユーザー（Codexの質問への回答） |
| 200件と64KBの上限 | 達したら出力する | ページを読み切った後に判定する排出の目安とする。1行の厳密な上限ではない | ユーザー（同上） |
| `--since`なしの初回 | 記載なし | `all`と同じく、初回の読み取りは基準として受け取り、通知しない | 監督役のレビューをCodexが採用 |
| 実行中コマンドの出力更新 | 記載なし | 出力だけが変わった更新では、settleの待ち時間を延長しない | 監督役のレビューをCodexが採用 |
| 「決めてほしいこと」の1〜3 | — | 推奨どおり（既定値は20秒と10分、方針の(2)(3)を既定に入れる） | ユーザー |
| 「決めてほしいこと」の4 | — | 通知選別とプロンプトを同じブランチで実装し、コミットを分けられるよう変更を混ぜない | 監督役の判断（ユーザーの決定ではない） |

検証: 2026-09-22、`npm test`は252件すべて成功（Codexの実行と、監督役による独立の実行の両方）。実運用での通知の削減率と遅延は未確認。
